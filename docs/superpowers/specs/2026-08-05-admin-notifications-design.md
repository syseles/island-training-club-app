# Admin Notifications Design

Date: 2026-08-05
Branch: `feature/notification`
Base: updated `feature/auth-identity`

## Goal

Give Admin and Super Admin users reliable in-app operational notifications for submitted applications, membership decisions, and security-relevant role changes while moving Notifications from crowded bottom navigation into the top bar.

## Branch Boundary

This branch contains both the approved Notification documentation and implementation. It is based on `feature/auth-identity` after shared UI/Admin improvements. It contains no Giving, Shop, merchandise, campaign, or FPS behavior.

## Notification Events

Every current Admin and Super Admin receives one notification for each event below.

### 1. Application submitted

Generated when an application first becomes submitted.

Example:

> **Membership application submitted**  
> Jordan Lee submitted a membership application.  
> 5 minutes ago · 5 Aug 2026, 2:32 PM HKT

Destination: `#/admin/approvals`

### 2. Application approved

Generated when a pending profile becomes a member through an application decision.

Example:

> **Application approved**  
> Jordan Lee was approved by Tina Chan.  
> 2 minutes ago · 5 Aug 2026, 2:35 PM HKT

Destination: `#/admin/members`

### 3. Application declined

Generated when a pending profile becomes declined through an application decision.

Example:

> **Application declined**  
> Jordan Lee was declined by Tina Chan.  
> Just now · 5 Aug 2026, 2:37 PM HKT

Destination: `#/admin/members`

### 4. Operational role changed

Generated for approved-user privilege changes:

- Member promoted to Admin
- Admin demoted to Member
- Member/Admin access revoked to Pending

Examples:

> **Member promoted**  
> Arnold Wong promoted Tina Chan from Member to Admin.

> **Admin demoted**  
> Arnold Wong changed Tina Chan from Admin to Member.

> **Membership revoked**  
> Arnold Wong revoked Jordan Lee’s member access.

Destination: `#/admin/members`

No notification is created merely because a Google-authenticated profile exists without a submitted application. Those users remain visible under Admin > Approvals > Awaiting application.

## Audience

- Deliver each operational notification to every profile whose role is `admin` or `super_admin` at event time.
- Include the acting administrator among recipients so the Notification page also serves as decision confirmation and an operational record.
- The affected member continues to receive existing member-facing notifications, including the current welcome notification on approval.
- Operational notifications do not replace the existing `role_changes` audit table.

## Database-Owned Delivery

Notifications are generated by Postgres triggers, not browser calls, so closing the app or losing network after an action cannot omit the event.

Create a new additive, rerunnable migration after the current Admin-decision migration. Do not edit previously applied migrations.

### Application submission trigger

Handle both insert and update safely:

- On insert: notify only when `submitted_at is not null`.
- On update: notify only when `old.submitted_at is null` and `new.submitted_at is not null`.
- Re-saving an already submitted application must not create a duplicate notification.

The trigger reads the applicant’s display name from `profiles` and inserts one `admin_application_submitted` notification per Admin/Super Admin.

### Role-change trigger

Replace the existing `record_role_change()` function with a backward-compatible definition that preserves:

- Every `role_changes` audit insertion
- Existing member welcome notification when the new role is `member`

Add operational notification classification:

- `pending -> member`: `admin_application_approved`
- `pending -> declined`: `admin_application_declined`
- `member -> admin`: `admin_role_promoted`
- `admin -> member`: `admin_role_demoted`
- `member/admin -> pending`: `admin_membership_revoked`

Other transitions remain audited but do not generate an operational notification unless added by a future migration.

The trigger resolves `auth.uid()` to the actor’s display name, with a safe “An administrator” fallback for service/admin operations without an authenticated profile.

### Data shape

Continue using the existing `notifications` table:

- `profile_id`: recipient Admin/Super Admin
- `kind`: stable event key listed above
- `title`: concise event title
- `body`: applicant/member and actor copy
- `created_at`: authoritative event timestamp
- `read_at`: per-recipient read state

Destination routes are mapped from stable `kind` values in the client, avoiding a schema change solely for links.

## Security and RLS

- Existing self-read/self-update Notification policies continue to ensure each recipient reads and marks only their own rows.
- Trigger functions use `security definer` with `set search_path = public` where required.
- Browser clients cannot create trusted Admin operational notifications.
- Notification bodies escape user-controlled display names when rendered.
- Admin destinations still enforce their existing route and RLS permissions.

## Navigation

### Bottom navigation

Remove Notifications from bottom navigation once the top-bar bell is operational. On the Auth branch this leaves Home, Schedule, Community, and Profile; when merged into Giving, approved/signed-in Giving navigation becomes the fifth product tab.

Admin remains available from Profile > Admin Tools and is not restored to bottom navigation.

### Top-bar bell

For signed-in users:

- Show a semantic 44×44px bell link/button in the top bar.
- Link to `#/notifications`.
- Display unread count when greater than zero.
- Cap visual text at `99+` while retaining the full accessible label.
- Use both badge/text and color; color alone is not the unread signal.
- Apply `aria-label`, such as “Notifications, 3 unread.”
- Use `aria-current="page"` when the Notification view is active.

Visitors do not see the bell.

Unread-count failure is non-blocking: retain the bell without a count and do not interrupt the current view.

## Notification Page

Render a proper page header and two sections for Admin/Super Admin:

1. **Club operations** — notification kinds beginning with `admin_`.
2. **My notifications** — member-facing notifications such as welcome messages.

Regular members see only **My notifications**.

Each notification is a semantic button or link—not an interactive `<div>`—and contains:

- Event title
- Body
- Relative time
- Exact Hong Kong date/time
- Unread dot plus stronger unread surface
- Descriptive accessible label/state

Empty states are section-specific. If the entire page is empty, explain that new notifications will appear there.

## Time Presentation

Use `created_at` as the source of truth.

Each row shows:

- Relative time: “Just now”, “5 minutes ago”, “2 hours ago”, “Yesterday”, or a concise older interval.
- Exact time in `Asia/Hong_Kong`, locale `en-HK`: e.g. “5 Aug 2026, 2:32 PM HKT”.

Relative formatting is a pure helper with deterministic date injection for tests. Exact formatting must not depend on the viewer’s machine timezone.

## Opening and Marking Read

When a user activates a notification:

1. Disable or mark the row busy to prevent duplicate updates.
2. Mark the notification read if unread.
3. On success, update the badge and navigate to the mapped destination.
4. If already read, navigate without an unnecessary write.
5. On mark-read failure, retain the page, restore the row, and show an accessible error; do not falsely navigate or decrement the badge.

Destination mapping:

- `admin_application_submitted` → `#/admin/approvals`
- All other `admin_*` kinds → `#/admin/members`
- Existing welcome/member notification without a dedicated destination → `#/account`

## Loading and Error Behavior

Reuse the shared Auth route/action feedback:

- Notification route marks `<main aria-busy="true">`.
- Previous screen remains during reads.
- Delayed loading feedback appears only after approximately 300ms.
- Query failure retains the previous screen and creates an accessible error toast.
- Bell-count failure remains silent/non-blocking.
- Mark-read failure is visible and truthful.

## Styling

Define all Notification classes used by the view; do not rely on undefined legacy `.row` classes. Provide:

- Padded section cards
- 44px semantic rows
- Unread dot/surface
- Title/body/time hierarchy
- Responsive wrapping
- Focus-visible ring
- Reduced-motion compliance

## Code Boundaries

- New Supabase migration: trigger definitions and event fan-out.
- `store.js`: list/read actions only; no localStorage shape change.
- `data.js` or `views.js`: pure relative/HKT time helpers, following existing helper ownership.
- `views.js`: bell HTML and semantic grouped Notification page.
- `app.js`: bell badge hydration and mark-read/navigation flow.
- `index.html`: top-bar bell host markup if a stable host is preferable to full rerender.
- `styles.css`: bell, badge, grouped page, row states.
- Smoke tests: SQL source contracts, view semantics, time formatting, read/navigation failures.

## Commit Boundaries

Use separate reviewable commits:

1. Document Notification behavior (this specification).
2. Add database trigger migration and SQL contract tests.
3. Add top-bar bell and grouped semantic Notification UI.
4. Add read/navigation/loading/error behavior and integration tests.

## Testing

Coverage must prove:

1. Application insert with `submitted_at` notifies every Admin/Super Admin once.
2. Transition from unsubmitted to submitted notifies once.
3. Editing an already submitted application does not duplicate notifications.
4. Incomplete profiles generate no notification.
5. Approval and decline produce the correct operational kind/body and preserve welcome behavior.
6. Promote, demote, and revoke produce the correct operational kinds.
7. Other transitions remain audited without unintended notifications.
8. Trigger definitions are rerunnable and preserve `record_role_change()` responsibilities.
9. Regular members cannot read Admin operational rows belonging to others.
10. Visitor header has no bell.
11. Signed-in header has a semantic 44px bell.
12. Bell displays accurate unread count and `99+` cap.
13. Bell-count failure does not break rendering.
14. Admin page groups Club operations and My notifications correctly.
15. Member page omits Club operations.
16. Notification rows are keyboard-accessible semantic controls.
17. Unread state is not communicated by color alone.
18. Relative time boundaries and exact HKT formatting are deterministic.
19. Opening an unread notification marks it read, updates count, and navigates correctly.
20. Already-read notifications avoid an unnecessary update.
21. Mark-read failure retains the page, restores controls, and avoids false navigation/count changes.
22. Existing auth, Admin, welcome notifications, Profile, and full smoke suites remain green.
